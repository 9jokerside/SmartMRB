## 一、项目简介

会议室是企业日常协作中频次最高、争用最激烈的共享资源，但管理方式往往相当原始：纸质登记表、群聊接龙、行政口头协调，导致四个典型问题——

| 问题 | 表现 |
| --- | --- |
| 预订方式落后 | 信息分散，谁在用、用到几点，其他人看不到 |
| 「撞会」频发 | 高峰时段一位难求，同时大量会议室订而不用 |
| 需求波动大 | 混合办公后跨楼层、跨部门协作增多，靠经验排期排不准 |
| 数据无法沉淀 | 利用率、空置率无从统计，空间规划只能凭经验 |

本系统用一个前后端分离的 Web 应用回应这四个问题：会议室状态实时可见、预约时自动校验冲突、按规则走审批、扫码签到、超时未签到自动释放，并把使用数据沉淀成可查询的统计报表。

> 本项目同时是本人的本科毕业设计课题，代码与文档会持续更新。

## 四、系统架构

前后端分离的五层结构，层与层之间通过接口解耦：

| 层次 | 组成 | 职责 |
| --- | --- | --- |
| 表现层 | Vue 3 · Vue Router · Pinia · Element Plus · ECharts | 页面渲染、交互、图表 |
| 接口层 | RESTful API · JWT 鉴权 · 统一响应 `{code, message, data}` | 路由、鉴权、参数校验 |
| 业务层 | 预约 · 审批 · 签到 · 统计 · 权限（Controller—Service） | 业务规则与事务边界 |
| 数据访问层 | MyBatis-Plus · 事务管理 · 行锁 / 乐观锁 | 持久化与查询优化 |
| 数据层 | MySQL 8.0（业务数据） · Redis（令牌 / 热点状态） | 存储与缓存 |

调用链：

```
浏览器 ──HTTP/JSON──▶ Nginx（静态资源） ──▶ Spring Boot ──▶ 业务层 ──▶ MyBatis-Plus ──▶ MySQL
                                                    └──▶ Redis（令牌 / 热点时段状态）
```

- 前端构建产物由 Nginx 托管，后端打成 Jar 包独立运行，两者通过 HTTP/JSON 通信；
- 分层的好处是后续接入电子门牌、门禁，或按用户/预约维度拆分微服务，都不需要推翻现有结构。

## 五、核心设计

### 5.1 预约冲突：时段表 + 唯一约束

会议室预约的本质是「同一空间、同一时间只能有一个人」，因此**不靠代码判断，而是让数据库保证插不进第二条**。

把每间会议室按 30 分钟切成格子，一次预约占用几个格子就写几行：

```sql
CREATE TABLE booking_slot (
  id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  booking_id  BIGINT       NOT NULL COMMENT '预约ID',
  room_id     BIGINT       NOT NULL COMMENT '会议室ID',
  slot_start  DATETIME     NOT NULL COMMENT '时段起点，如 09:00 / 09:30',
  PRIMARY KEY (id),
  UNIQUE KEY uk_room_slot (room_id, slot_start)
) ENGINE = InnoDB COMMENT '时段占用表';
```

一次 09:00—10:30 的预约会写入 09:00、09:30、10:00 三行。任何重叠的预约（例如 10:00—11:00）都会因为 `10:00` 这一格已存在而**在插入时直接失败**。

这样做的收益：

- 冲突检测从「算法问题」变成「数据结构问题」，不存在漏判；
- 不需要分布式锁——单实例部署下 `@Transactional` 保证多行写入的原子性已经足够；
- 并发抢订时只会有一个事务成功，其余捕获唯一键冲突并返回「该时段已被预约」。

配合前端时间轴（空格可点、占用格置灰），用户几乎不会提交到冲突的时段。

### 5.2 预约状态机

七个状态、十一条迁移，「超时未签到自动释放」是一等状态，而不是异常分支。

主干路径：`新建 → 已通过 → 待签到 → 使用中 → 已完成`；分支为 `新建 → 待审批 →（通过 / 驳回 / 取消）`、`待签到 →（超时未签到）已释放`。

完整迁移表：

| 当前状态 | 触发动作 | 下一状态 | 说明 |
| --- | --- | --- | --- |
| 新建 | 提交（免审批） | 已通过 | 直接占用时段 |
| 新建 | 提交（需审批） | 待审批 | 进入审批队列 |
| 待审批 | 审批通过 | 已通过 | 生成签到码 |
| 待审批 | 审批驳回 | 已驳回 | 释放时段，通知申请人 |
| 待审批 | 申请人取消 | 已取消 | 释放时段，通知审批人 |
| 已通过 | 到达开始前 15 分钟 | 待签到 | 推送提醒 |
| 待签到 | 扫码签到 | 使用中 | 记录签到时间 |
| 待签到 | 超过开始后 15 分钟 | 已释放 | 定时任务自动处理 |
| 使用中 | 到达结束时间 | 已完成 | 正常结束 |
| 使用中 | 提前结束 | 已完成 | 立即释放会议室 |
| 已通过 / 待签到 | 开始前 30 分钟外取消 | 已取消 | 释放时段 |

关键规则：

- 开始前 30 分钟以上可自行取消；已签到不可自行取消，只能「提前结束」；
- 开始后 15 分钟内未签到，定时任务将预约置为**已释放**并推送消息；
- 每条迁移都带守卫条件（时间窗、角色、当前状态），服务端统一校验。

### 5.3 审批规则

审批不是写死的两级流程，而是「三条件查表」：

| 会议室审批级别 | 单次时长 | 跨部门 | 审批路径 |
| :-: | :-: | :-: | --- |
| 0（普通） | ≤ 2 小时 | 否 | 免审批，直接通过 |
| 0（普通） | > 2 小时 | 任意 | 部门负责人 |
| 1（重要） | 任意 | 任意 | 部门负责人 |
| 2（贵宾/大会议室） | 任意 | 任意 | 行政管理员 |
| 任意 | 任意 | 是 | 行政管理员 |

改一个会议室的审批级别，审批人随之变化；每次审批的节点、审批人、意见、时间写入 `booking_approval`，可追溯。

### 5.4 会议室推荐

先硬约束过滤，再软因素打分，把「人找资源」变成「资源找人」：

```
可用会议室 = 满足时间段 ∩ 容量 ≥ 参会人数 ∩ 设备齐备 ∩ 状态启用

Score = w₁·容量匹配度 + w₂·设备满足度 + w₃·历史偏好 + w₄·楼层距离
```

- 容量匹配度：参会人数与容纳人数越接近得分越高（避免 3 人占用 30 人会议室）；
- 设备满足度：所需投影 / 视频会议 / 白板是否齐备；
- 历史偏好：本人及所在部门过去常选的楼层与房型；
- 楼层距离：与申请人所在楼层越近越优先；
- 权重 `w₁~w₄` 可在系统参数中配置，初期取经验值，后续可根据实际选择数据调整。

## 六、数据库设计

共 17 张核心表，按四个域组织：

| 域 | 表 | 说明 |
| --- | --- | --- |
| 权限域 | `sys_user` `sys_role` `sys_permission` `sys_user_role` `sys_role_permission` `sys_dept` | 用户、角色、权限、部门 |
| 资源域 | `meeting_room` `device` `room_device` | 会议室台账、设备台账、关联表 |
| 业务域 | `booking` `booking_slot` `booking_attendee` `booking_approval` `checkin_record` | 预约主表、时段占用、参会人、审批记录、签到记录 |
| 支撑域 | `sys_notification` `sys_oper_log` `sys_config` | 通知、操作日志、参数配置 |

关键约束：

- `booking_slot`：`UNIQUE(room_id, slot_start)` —— 防重复预订的底线；
- `checkin_record`：`UNIQUE(booking_id)` —— 一条预约只能有效签到一次；
- `booking`：`INDEX(book_date, room_id, status)`、`INDEX(user_id, status, book_date)` —— 支撑时段查询与「我的预约」。

## 七、接口一览

统一响应结构，除登录外均需 `Authorization: Bearer <token>`：

```json
{ "code": 0, "message": "success", "data": {} }
```

| 模块 | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 认证 | POST | `/api/auth/login` | 登录，返回 token |
| 认证 | POST | `/api/auth/logout` | 退出，令牌加入黑名单 |
| 会议室 | GET | `/api/rooms` | 条件分页查询 |
| 会议室 | GET | `/api/rooms/{id}/schedule` | 某会议室某日/某周占用 |
| 会议室 | GET | `/api/rooms/available` | 按时间、人数、设备查可用会议室 |
| 预约 | POST | `/api/bookings` | 提交预约（校验冲突与容量） |
| 预约 | GET | `/api/bookings` | 分页查询（按角色限定数据范围） |
| 预约 | PUT | `/api/bookings/{id}/cancel` | 取消预约 |
| 审批 | GET | `/api/approvals` | 待审批列表 |
| 审批 | POST | `/api/approvals/{id}/approve` | 审批通过 |
| 审批 | POST | `/api/approvals/{id}/reject` | 审批驳回 |
| 签到 | POST | `/api/checkin` | 扫码签到 |
| 统计 | GET | `/api/stats/rooms` | 会议室使用统计 |
| 系统 | GET | `/api/logs` | 操作日志查询 |

完整接口文档在启动后端后访问 `http://localhost:8080/doc.html`（Knife4j）。

主要错误码：`1001` 参数错误、`1002` 未登录或令牌失效、`1003` 无权限、`2002` 时段已被占用、`2003` 超出可预约时间范围、`3001` 签到已过期。

## 十一、常见问题

**Q：为什么不用现成的钉钉 / 飞书会议室功能？**
通用产品的审批规则、会议室分级、统计口径都是固定的，企业按自己的流程改不了；本项目的目的是完整实践需求分析、架构设计与并发正确的实现，这些在成品里是黑盒。

**Q：并发抢订真的不会重复吗？**
不会。冲突由数据库唯一约束保证：同一会议室同一 30 分钟时段只允许一行 `booking_slot`，插入冲突即回滚并返回「已被预约」。压测时用 50 个并发请求抢同一时段，只会成功 1 条。

**Q：为什么时间粒度是 30 分钟？**
企业会议多以半小时为单位，一天切成 18 段左右时间轴可读。粒度做成了系统参数，需要时可以调整。

**Q：签到能不能代签？**
签到码带签名参数（预约 ID、会议室、有效时间窗），服务端校验签名与时间窗，过期或篡改都会被拒；更严格的方式是后续接入门禁或人脸识别。
